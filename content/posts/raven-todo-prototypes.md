Raven Todo 的第一版，我给自己定了一条很朴素的标准：连续十天，所有要做的事都只记在这里。做得到，它就有用；做不到，功能再多也没意义。

问题是，“界面长什么样”很难在脑子里想清楚。三个模糊的方案在脑中打架，可以耗掉一整天。所以这次在写任何 Swift 之前，我先做了原型。

## 为什么是一次性的原型

原型只回答一个问题：主窗口长什么样。它是一个 HTML 文件，数据只存在内存里，刷新就没了；底部有一条黑色的小工具条，左右箭头切换方案，还有一个按钮能清空列表，看空状态。

“一次性”很重要。它允许原型不写测试、不处理异常、不管持久化，只管让我尽快看到、摸到。选定以后，原型不进主分支，单独放在一个 `prototype/` 分支里，留作当时为什么这样选的证据。

## 第一轮：三种清单

第一轮是三个结构完全不同的方案：

- **单列清单**：输入框在上，“今天”是列表里的一个分组；
- **今天 / 以后两栏**：两列并排，各自有输入框，箭头按钮把任务挪到另一列；
- **底部输入**：像聊天一样在底部输入，顶部用“全部 / 今天 / 已完成”切换。

三个都能用，但都不对。试的时候我发现自己真正想做的事，是**晚上把明天要做的事排好，第二天一打开它们就在“今天”里**。清单式的界面表达不了“时间在推进”。

## 第二轮：按时间分组的看板

于是第二轮直接换了方向：三列看板，**待办、今天、明天**，各用一种颜色——待办是 violet，今天是 amber，明天是 blue，都取自 Radix Colors。任务有标题、详情和可选的时间，可以在列之间拖动。

这一轮同样做了三个变体：三列等宽、“今天”占主位、一张菜单栏小卡片。最后选的是最朴素的三列等宽。理由很简单：三列等宽时，“把任务从右边拖到中间”这个动作最自然。

## 把“列”交给日期

原型里最有价值的发现不是视觉，而是一条规则：**任务不存“属于哪一列”，只存日期**。

| 日期 | 所在的列 |
| --- | --- |
| 没有日期，或在明天之后 | 待办 |
| 明天 | 明天 |
| 今天，或更早还没完成 | 今天 |

这样一来，零点一过，什么都不用做，昨晚排在“明天”的任务自己就到了“今天”。没完成的旧任务也留在“今天”，行尾标一个红色的“昨天”。

原型里有一个“下一天”按钮专门模拟零点，点一下就能验证这条规则。到了正式的 App 里，这条规则写在一个不依赖界面的模块里，用测试固定下来：

```swift
public init(day: Day?, today: Day) {
  guard let day else { self = .backlog; return }
  if day <= today { self = .today }
  else { self = day == today.adding(days: 1) ? .tomorrow : .backlog }
}
```

## 留下的几个“先这样”

有些问题原型里没想清楚，我选择先用最简单的做法，并且把它们写进决策记录：

- 顺延过来的任务排在原位置，不自动置顶；
- 带时间的任务不自动按时间排序，顺序由拖动决定；
- 菜单栏卡片暂时不做，只在菜单里列出今天的任务。

等真的用上十天，再看哪一条最让人难受。原型的意义也在这里：它帮你尽快做出一个**可以被推翻**的决定。
